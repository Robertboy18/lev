Getting started

Install lev, inspect the machine once, then use the Lake project already in front of you.

Install

Terminal
cargo install --git https://github.com/Robertboy18/lev --locked lev-cli
lev --version
lev doctor

What doctor checks. The report identifies the cache, Git, the optional elan fallback, the discovered project, its selected runtime, Lean and Lake, and any lev configuration. A failed probe names the layer to repair; doctor itself never modifies state.

To uninstall, first preview the selected executable with lev self uninstall --dry-run. A Cargo-managed installation is handed back to Cargo; cache and toolchain data are retained unless you remove them separately.

Shell completions

lev completions prints a completion definition for a supported shell on stdout. Install it where the shell already looks for completions, then open a new shell session.

Terminal
# Bash
lev completions bash > ~/.local/share/bash-completion/completions/lev

# Zsh (any directory on $fpath)
lev completions zsh > ~/.zfunc/_lev

# Fish
lev completions fish > ~/.config/fish/completions/lev.fish

The definition is generated by the installed binary, so re-run the command after upgrading lev.

Use an existing project

I wanted adoption to be boring in the best sense. A Lake project should not need a migration before lev can help. lev reads the ordinary lean-toolchain, Lakefile, and manifest, then adds lev.lock for the extra environment and integrity data it owns.

Discover and synchronize

Run from the root or a subdirectory. sync installs or selects the toolchain, materializes dependencies, and prepares compatible shared state.

Terminal
cd my-formalization
lev sync

Build through Lake

The short command performs the common preflight and delegates to lake build.

Terminal
lev build
lev test
lev lint

Lock the result

Commit lev.lock alongside the existing Lake files so CI and another checkout can verify the same environment.

Terminal
lev lock
git add lev.lock lean-toolchain lake-manifest.json
git commit -m "Lock Lean environment"

Create a project

Create
lev init theorem-playground --lean stable
cd theorem-playground
lev build
Project shape
theorem-playground/
├── TheoremPlayground/
├── Main.lean
├── lakefile.toml
├── lean-toolchain
└── lev.lock

init creates a standard Lake package. The toolchain selector is resolved through the configured source rather than a release list compiled into lev.

The daily loop

IntentCommandWhat happens
Update local statelev syncReproduce the locked toolchain and dependencies.
Buildlev build [TARGET]Prepare the environment, then invoke Lake.
Run a processlev run -- COMMANDExecute any process with the selected Lean environment attached.
Check one filelev check Path/File.leanElaborate the file through its Lake environment.
Work offlinelev build --offlineRefuse implicit toolchain or dependency network access.
Explain orchestrationlev -v buildShow cache and environment decisions in addition to Lake output.
No shell activation. Each lev command attaches the selected environment to the child process. Closing the shell does not lose or mutate an activated state.

When the first run fails

A failed first run is usually easier to fix once you know which layer refused it. lev errors describe environment selection and orchestration; Lake and Lean still print their own build diagnostics. Two failures that look similar in a terminal can call for very different repairs.

Lock drift
$ lev sync --frozen
error: effective Lake configuration for
leanprover/lean4:v4.19.0 does not match lev.lock
Captured delegated build failure
$ lev build --no-sync --offline MissingTarget
error: unknown target `MissingTarget`
lev: Lake build failed under leanprover/lean4:v4.18.0 with exit code 1;
retry trusted hash metadata with `lev build --no-sync --rehash TARGET`

Captured on August 4, 2026 from the dependency-free Lean 4.18.0 scratch project used throughout this manual.

Lock drift means a project input changed after lev.lock was written. If you deliberately edited the Lakefile, manifest, or toolchain, run lev lock, review the lock diff, and commit both changes together. If you did not mean to change the environment, restore the changed project file and keep the existing lock.

A delegated failure means lev reached Lake and Lake returned a nonzero status. Read the Lean or Lake diagnostic above lev's summary first. The focused --rehash TARGET retry is useful when trusted file-hash metadata is stale; it is not a general way to hide a theorem or compilation error.

A useful diagnosis pass
lev doctor
lev lock --check
lev -v --timings build

-v shows environment, dependency, and cache decisions. --timings shows whether time was spent preparing the environment, waiting for shared-state locks, or inside the delegated command. Keep the failing output from both streams when reporting a problem.

Do not begin by deleting .lake. That throws away evidence and can turn a small lock or source error into a full rebuild. Check the lock, read the delegated diagnostic, and use the focused retry first. Clean only when the output points to stale generated state.

Add and update dependencies

For declarative lakefile.toml projects, add and remove edit dependencies transactionally. Lake remains responsible for resolving the resulting manifest.

Examples
lev add mathlib
lev add plausible --rev v0.2.0
lev remove plausible
lev update

# Review compatible direct-dependency releases first
lev outdated
lev upgrade --dry-run
lev upgrade mathlib
Preview upgrades before applying them. A dependency release can be compatible with the selected Lean version and still require source changes in your project. --dry-run makes the intended transaction reviewable.

What lev adds to the checkout

lev works with the files a Lake project already commits and adds a small number of its own. Everything below is plain text and reviewable in version control.

FileWritten byCommit it?Purpose
lean-toolchainProjectYesThe toolchain selector Lake and elan already understand.
lakefile.toml / lakefile.leanProjectYesLake package configuration. lev add and lev remove edit the declarative TOML form.
lake-manifest.jsonLakeYesResolved package dependencies. Never edit it by hand.
lev.locklevYesEnvironment identity and integrity data for reproduction and audit.
lev.tomlYouWhen usedOptional [workspace] members and named [tasks].
lev-workspace.locklevIn workspacesAggregate lock, published only after every member sync succeeds.

None of these replaces a Lake file. Deleting lev.lock returns the project to plain elan-and-Lake behavior; regenerating it with lev lock restores the reproducibility guarantees.
