Core guide

Verification and automation

Turn the shell loops and release checklists around Lake into explicit, inspectable project workflows.

One ordered verification gate

This part of lev began with the sort of release checklist that lives in shell history: check the lock, audit dependencies, build, test, lint, and remember the import check. The easiest check to miss is the one nobody wrote down. lev verify runs those gates in a stable order, stops at the first failure, and preserves delegated exit status.

Release-style gate
lev verify
lev verify --clean --offline --strict --test --lint --imports
lev verify --offline --test -- MyLibrary
lev verify --json > verify.json
Captured verification report
Build completed successfully.
PASS  lock             0.436 ms  lev.lock matches project configuration and manifest
PASS  audit            0.175 ms  3 passed, 0 warnings, 0 errors
PASS  toolchain      142.340 ms  leanprover/lean4:v4.18.0 is available
PASS  build          305.334 ms  lake build

Captured on August 4, 2026 from a dependency-free Lean 4.18.0 project copied to local scratch. Optional test, lint, and import phases appear when their flags are present.

--clean inserts lake clean before the build. --strict promotes audit portability warnings to failures. Arguments after the options are appended to lake build, not to test or lint.

What a failed JSON gate records

The report contains only phases that actually completed. If the build fails, test, lint, and imports do not appear as skipped successes; they are absent because lev stopped at the build boundary. The command returns Lake's exit code.

    "project": "/tmp/lev-doc-profile.GP0wJ1/project",

Compiler diagnostic on stderr
error: unknown target `MissingTarget`

With --json, the one JSON document stays on stdout while Lake diagnostics go to stderr. That lets CI save the report even when the gate fails without mixing compiler text into the JSON file.

Review dependency upgrades

Plain lev update remains the direct Lake update path. For a reviewable Reservoir-aware transaction, separate discovery from application.

Inspect compatible releases

Terminal
lev outdated
lev outdated --check
lev outdated --json > outdated.json

--check returns status 1 when a compatible update exists, which is useful for scheduled CI. The report distinguishes five states: current, outdated (a compatible newer release exists), incompatible (newer releases exist but none match the selected Lean), unmanaged (not resolvable through the Reservoir index, for example a plain Git dependency), and unavailable (the index could not be consulted). Only outdated entries trigger the --check exit code.

Preview the transaction

Terminal
lev upgrade --dry-run
lev upgrade mathlib --dry-run
lev upgrade --group algebra --dry-run
lev upgrade --lean leanprover/lean4:v4.20.0 --dry-run

Apply deliberately

Terminal
lev upgrade mathlib
lev verify --test --lint

The upgrade updates project state transactionally; project source compatibility still belongs to the subsequent build and tests.

Compatibility metadata narrows the search. The project build and tests remain the proof obligation because a package release indexed for the selected Lean toolchain can still change APIs your project uses.

Operate on a workspace of Lake roots

A lev workspace is an ordered set of independent Lake projects declared in the nearest ancestor lev.toml. Each member keeps its own toolchain, manifest, lock, and transaction boundary.

lev.toml
[workspace]
members = [
  "library",
  "examples",
  "benchmarks",
]
Workspace commands
lev workspace list
lev workspace lock
lev workspace lock --check
lev workspace sync --frozen
lev workspace build --offline --keep-going
lev workspace run --keep-going -- lake test
Workspace list
benchmarks  leanprover/lean4:v4.18.0
examples    leanprover/lean4:v4.19.0
library     leanprover/lean4:v4.19.0

Members run in deterministic path order. Without --keep-going, the first failing member stops the operation. With it, lev continues and returns the first failure code. The aggregate lev-workspace.lock is published only after every member sync succeeds, so it never describes a partial success as complete.

During a kept-going build, lev prints lev: workspace build: MEMBER before each member. If examples exits with status 37, lev still visits the later members and the workspace command finally returns 37. --keep-going finishes collecting results; it never converts a failed member into success.

Build, run, sync, and lock use human-readable progress and process exit codes. The two workspace JSON contracts are workspace list --json and workspace shake --json.

Minimize imports across the workspace

Conservative workspace policy
lev workspace shake \
  --check \
  --keep-public \
  --keep-implied \
  --keep-going

lev workspace shake \
  --fix \
  --isolate \
  --keep-public \
  --keep-implied \
  --keep-going

lev workspace shake --check --json > workspace-shake.json
lev workspace shake --check --sarif workspace-shake.sarif

There are two kinds of isolation here. Each Lake member has its own source transaction, and --isolate can further separate accepted and rejected edits within a member. Aggregate JSON uses lev.cli.workspace.shake/v1 and retains each member's exit code and report.

Create a deterministic source bundle

lev bundle creates a Zstandard-compressed tar archive of locked project sources. Generated trees and transient lev outputs are excluded, and repeated bundles from the same source state are deterministic.

Bundle a handoff
lev verify --offline
lev bundle
lev bundle --output artifacts/algebra-notes.lev.tar.zst
lev bundle --force --output artifacts/algebra-notes.lev.tar.zst
Captured bundle output
lev: bundled 21 files (11237 source bytes) into /tmp/lev-doc-bundle-20260804.lev.tar.zst

Captured on August 4, 2026 from the dependency-free scratch project used elsewhere in this manual.

The default destination is <project>.lev.tar.zst in the current directory. Existing destinations are refused unless --force is explicit. A bundle is a reproducible source handoff, not a replacement for Git history or a guarantee that the receiving machine already has every toolchain object.

Keep the selected environment in the edit loop

Watch examples
# Run lake build immediately, then after relevant changes
lev watch

# Check one file after edits settle for 400 ms
lev watch --debounce-ms 400 -- \
  lake env lean MyProject/Proof.lean

# Useful in bounded automation
lev watch --max-runs 5 --exit-on-failure -- lake test

# Wait for the first edit
lev watch --no-initial
Captured one-run watch session
lev: watching /tmp/lev-doc-profile.GP0wJ1/project and running `lake build`
lev: watch run: lake build
Build completed successfully.

Captured with lev watch --max-runs 1 --no-sync --offline on August 4, 2026. The run bound lets the example finish without waiting for a file edit.

The watcher is event-driven and debounced. It ignores generated and dependency trees such as .git, .lake, build, lake-packages, and target, as well as lock outputs produced by the run itself. A failed command normally leaves the watcher alive so the next edit can repair it; --exit-on-failure changes that behavior.

Project tasks and scripts

Tasks give repeated project commands a versioned name without hiding the underlying process.

lev.toml
[tasks]
docs = ["lake", "build", "Documentation"]
smoke = ["lake", "test", "--", "smoke"]
Terminal
lev task
lev task docs
lev task smoke -- --seed 42

Everything after the task name and -- is appended to the configured command, so a task can stay minimal while callers add options per run. lev task with no name lists the configured tasks, which makes the available automation discoverable from the checkout itself.

For a single Lean file outside a permanent package, lev script can build a cached inline environment from metadata in the file. Use a normal Lake package once the code has multiple modules, public targets, or a release lifecycle.

Script with inline metadata
-- /// lev
-- lean = "leanprover/lean4:v4.19.0"
-- [[dependencies]]
-- name = "mathlib"
-- scope = "leanprover-community"
-- ///

import Mathlib.Data.Nat.Prime.Basic

#eval Nat.minFac 91
Terminal
lev script run Example.lean
lev script check Example.lean

The inline block declares the toolchain and dependencies the file needs. lev materializes a cached environment for that combination, so the second run of the same script skips the setup cost. check elaborates without running.

Inspect the dependency graph

Three commands answer the questions that otherwise require reading lake-manifest.json by eye. All of them read recorded state; none of them modifies the project.

Terminal
# Flat inventory recorded by the manifest
lev deps

# Resolved dependency tree with revisions
lev tree

# Which requirement chain pulls this package in?
lev why batteries
Why output
mathlib -> batteries

why is the one to reach for when a package appears in the manifest that nobody remembers adding: it prints the requirement chain from a direct dependency down to the package in question.

Audit integrity and export an SBOM

lev audit checks that local state still matches what the lock recorded: lock consistency, toolchain integrity, and dependency checkout hashes. It reads and verifies; it never repairs silently.

Terminal
lev audit
lev audit --json > audit.json

# Dependency inventory for compliance tooling
lev export --format cyclonedx -o lev-sbom.json

The CycloneDX export lists the exact resolved dependencies from the locked environment, which lets standard supply-chain tooling consume a Lean project without a custom parser. audit --json uses the lev.cli.audit/v1 envelope, and verify runs the same audit as its second phase.

A compact CI example

GitHub Actions step
- name: Verify locked Lean project
  run: |
    lev sync --frozen
    lev verify --offline --strict --test --lint --imports
    lev bundle --output artifacts/source.lev.tar.zst

- name: Save verification report
  if: always()
  run: lev verify --offline --json > artifacts/verify.json

In a real workflow, install lev at a reviewed revision and restore the configured lev cache before sync. Keep the JSON report even on failure; it records which phase established the boundary.
