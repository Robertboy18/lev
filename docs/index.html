Lean environments that remember their work

lev coordinates Lean toolchains, Lake dependencies, locks, and compatible build artifacts without replacing the files Lean projects already use.

lev 1.0Standard Lake projectsLocal and CI workflows

Why lev exists

I kept coming back to one practical annoyance: a second checkout should not forget everything the first checkout already downloaded, resolved, and built. Lake is excellent at building a package, and elan selects Lean toolchains. The repeated work appears between projects, worktrees, benchmark runs, and CI jobs.

lev sits around the normal Lean stack. It resolves the requested environment, verifies locks, attaches shared stores, and then delegates the actual build or command. Your Lakefile, lean-toolchain, and lake-manifest.json remain useful without lev.

You may not need lev for one stable project. If elan and Lake already make that project reliable, keep the smaller toolchain. lev becomes useful when several environments must remain isolated but should still reuse compatible work.

A first look

The daily loop is intentionally boring. There is no activation step and no lev-specific package format. Run lev from any directory inside the project and it discovers the nearest Lake root.

Terminal
cd algebra-notes
lev sync
lev build
Captured scratch-project run
lev: already synchronized 0 Git dependencies:
0 created, 0 reused, 0 updated;
0 mirrors created, 0 fetched
Build completed successfully.

Captured with lev -v build on August 4, 2026 from a dependency-free Lean 4.18.0 project. A project with Git dependencies reports nonzero created, reused, updated, mirrored, and fetched counts before Lake's build output.

lev sync materializes the locked environment. lev build performs the same preflight and then invokes lake build. Add --offline when the run must prove it can use only local state.

Where lev stops

lev takes care of the environment around a Lean project. The proofs and build graph still belong to Lean, Lake, and the project itself.

  • If a Lean release changes source compatibility, lev can isolate the old and new environments; it cannot migrate the proofs.
  • If Lake cannot build the project, lev cannot repair Lake's target graph. It reports the delegated failure and preserves its exit code.
  • Cached artifacts are reused only across matching compatibility keys and after integrity checks. A cache hit is an optimization, never the source of truth.
  • Import analysis can discover declaration dependencies, but public re-exports and namespace-only effects encode human API intent. Conservative policies and a full rebuild remain necessary.
