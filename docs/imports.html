Imports and module graphs

Let the compiler tell you what a file uses, but let the project decide what its public API promises.

The broad-import problem

Import minimization started with a familiar file: it imports all of Mathlib but uses one small corner of it. import Mathlib is convenient while exploring. In a mature file it can conceal the actual dependency surface, increase invalidation, and make the module graph harder to reason about. Replacing it manually is tedious because source text does not reveal every elaborated declaration dependency.

Before
import Mathlib

example (n : ℕ) : n ∣ n := by
  exact dvd_refl n
Possible result
import Mathlib.Algebra.Divisibility.Basic

example (n : ℕ) : n ∣ n := by
  exact dvd_refl n

The exact module depends on the Mathlib revision. lev computes it from the version your project actually uses.

How lev shake works

lev imports is a descriptive alias for lev shake. It runs Lake's import analysis in the selected environment, interprets the compiler-derived dependency metadata, and wraps any edit in a validation transaction.

  1. Discover target modules from explicit arguments or the package's default targets.
  2. Ask the selected Lake toolchain for import suggestions based on compiled dependencies.
  3. Apply policy such as preserving public or implied imports and explicit keep annotations.
  4. With --fix, snapshot source files, apply suggestions, bypass stale artifact reuse, and rebuild.
  5. Keep verified changes. On failure, restore the originals; with isolation enabled, retain only independently verified subsets.

Preview, check, and apply

One module
lev imports MyProject.Proof --explain
lev imports MyProject.Proof --check
lev imports MyProject.Proof --fix
Import preview
MyProject/Proof.lean:
  remove #[import Mathlib]
  add #[import Mathlib.Data.Nat.Prime.Basic]

The module names come from the project's pinned Lake and dependencies.

Conservative project-wide pass
lev imports \
  --keep-public \
  --keep-implied \
  --explain

lev imports \
  --keep-public \
  --keep-implied \
  --fix \
  --isolate

--check changes no source and exits unsuccessfully when drift is found, which makes it useful in CI. --fix applies and validates; --apply is an equivalent spelling. --isolate turns a failing batch into smaller verification units so accepted edits do not have to be discarded with an unrelated rejected file.

Successful apply
$ lev imports --fix
Successfully applied 1 suggestions.
lev: verifying rewritten imports
Build completed successfully.

$ lev imports --fix
lev: imports are already minimal
Failed apply and rollback
$ lev imports --fix
lev: verifying rewritten imports
error: unknown constant 'Nat.prime_five'
lev: import verification failed; restoring the original Lean sources
$ echo $?
1

Running the command again should produce no new edits. That fixed point is a useful check that the accepted source and the analyzer agree. On failure, lev restores the original bytes before returning, so the working tree is not left halfway through an import rewrite.

When one file rejects the batch

Suppose A.lean can use the smaller imports but B.lean relies on a namespace effect that does not appear as a declaration edge. With --isolate, lev verifies the restored baseline, tests smaller subsets, keeps A.lean, and restores B.lean.

Isolated partial result
$ lev imports --fix --isolate --json > shake.json
lev: batch verification failed; isolating import edits
lev: verifying the restored baseline
lev: rejected the import rewrite for B.lean
lev: keep the dependency with `import Mathlib -- shake: keep`
$ echo $?
1
shake.json
{
  "schema": "lev.cli.shake/v1",
  "data": {
    "mode": "isolate",
    "status": "partially_applied",
    "files": [
      { "path": "A.lean", "disposition": "applied" },
      {
        "path": "B.lean",
        "disposition": "rejected",
        "keep_annotations": [
          "import Mathlib -- shake: keep"
        ]
      }
    ]
  }
}

Status 1 is intentional here: useful edits were kept, but the requested whole-project minimization did not fully succeed. Review the retained diff, add the suggested keep annotation when it matches project intent, and run the command again.

FlagEffect
--explainPreview each proposed edit with the declaration that requires it.
--checkReport drift without touching sources; nonzero exit when changes exist.
--fix / --applyRewrite sources inside a validation transaction.
--isolateOn failure, split the batch and keep independently verified subsets.
--keep-publicPreserve public imports as deliberate re-export policy.
--keep-impliedPreserve imports implied by transitive library boundaries.
--keep-prefixPrefer a broader convenience module over its exact leaf imports.
--no-build / --forceSkip the automatic rebuild of stale .olean files before analysis.

Requirements and behavior to know

  • The selected Lake toolchain must provide its native shake command; older toolchains without it cannot run the analysis.
  • Analyzed files must use the Lean module system (a leading module command). Legacy files are reported, not silently skipped.
  • Stale .olean files are rebuilt automatically before analysis unless --no-build or --force says otherwise, because suggestions derived from stale artifacts would be wrong.
  • Validation builds bypass Lake's artifact cache and end with a freshness check, so a cache hit cannot mask a missing .olean.
  • If the whole-batch rewrite fails under --isolate, lev restores and verifies the baseline first. A broken baseline leaves every file unchanged; a partial result exits with status 1 and reports candidate -- shake: keep annotations for the failing files.

Know what was actually analyzed

A clean check is only as strong as its coverage. --coverage reports which project files Lake's analysis actually saw, so “no drift” cannot silently mean “nothing was inspected.”

Coverage report
lev imports --check --coverage
lev imports --check --coverage --json

Coverage separates project Lean files into three groups: module files analyzed under the selected roots, module files outside those roots, and legacy files without a leading module command. The JSON envelope (lev.cli.shake/v1) includes each proposed, applied, rejected, or restored file, which makes the report diffable across CI runs.

Compiler evidence is not API intent

A declaration dependency tells us what the current implementation references. It cannot always tell us why an import is present.

Import roleCompiler can usually see it?Policy
Declaration used in a proofYes, through elaborated dependenciesSafe candidate for inference
Public re-exportNot as downstream API intentBegin with --keep-public
Namespace or scoped notation effectNot always as a declaration edgeKeep explicitly when required
Implied/transitive boundaryMay look redundant locallyUse --keep-implied for libraries
Explicit project intent
import Mathlib.NumberTheory.NumberField.Basic -- shake: keep

-- The import is part of this module's public surface even when
-- the implementation below has no direct declaration edge to it.

Inspect the module graph

lev graph reads project source imports without crawling generated build trees. Roots can be module names or Lean file paths and can be repeated.

Graph reports
lev graph MyProject.Main
lev graph MyProject.Main MyProject.Tests --external
lev graph MyProject.Main --format json -o imports.json
lev graph MyProject.Main --external --format dot -o imports.dot
dot -Tsvg imports.dot -o imports.svg
Graph output
3 modules, 3 edges, 0 cycles
MyProject.Main  MyProject/Main.lean  direct=2 external=0 transitive=2
  -> MyProject.Algebra
  -> MyProject.Util
MyProject.Algebra  MyProject/Algebra.lean  direct=0 external=1 transitive=0
  -> Mathlib.Algebra.Group.Basic
MyProject.Util  MyProject/Util.lean  direct=0 external=0 transitive=0

--external includes modules outside the project and renders them as dashed boxes in DOT. The Graphviz dot command is separate software. lev graph exits unsuccessfully if it detects a cycle.

Case study: the FLT project

A toy file can show the mechanism, but I wanted to know what happened when a real library pushed back. On July 28, 2026, lev was evaluated on Imperial College London's FLT formalization at commit 0996e0c. The checkout contained 269 Lean files; the default FLT target exposed 259 module-system files to Lake's analysis.

Baseline
8,920 jobs / 196.79 s
First preview
119 files proposed
Verified result
34 files / +9 −54

Establish the baseline

A complete 8,920-job Lake build passed. That exact target, rather than a small demonstration module, became the validation boundary.

Let the aggressive pass fail

The first preview proposed 119 files. Applying all suggestions broke 10 modules, so lev restored every source from its transaction snapshot.

Preserve library intent

--keep-public reduced the proposal to 76 files but left one failure. Adding --keep-implied reduced it to 34, exposing the difference between implementation dependencies and re-export policy.

Annotate two exceptions

Two namespace-only imports received -- shake: keep. lev rewrote 33 other files, the complete target passed in 228.04 seconds, and a repeated minimization run found no remaining changes.

The case study changed lev. It exposed a false-positive verification path where Lake's artifact cache could report success without producing a changed .olean. Import validation now bypasses that cache and checks freshness before accepting edits.

The timing difference between baseline and validation is not evidence that minimization makes builds slower or faster by a fixed amount. The tested result is narrower: a verified smaller import surface, complete rollback on failure, and a stable fixed point on a large formalization.

Put import policy in CI

Machine-readable checks
lev imports --check --json > shake.json
lev imports --check --sarif lev-shake.sarif
lev verify --offline --imports

JSON uses the stable lev schema envelope. SARIF is suitable for review annotations. verify --imports places drift detection after lock, audit, toolchain, and build checks, so the report stops at the first broken prerequisite.
